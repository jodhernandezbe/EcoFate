## Goals / Non-Goals

**Goals:**
- A hiring manager understands the problem and sees the app, the evaluation result and the
  monitoring dashboard in the first two screens.
- A peer can score every criterion from one README section each, with a link to the code and
  a command to run, and can verify claims without an API key (screenshots, checked-in
  reports and numbers).
- Self-evaluation is honest: unmet items are shown as unmet.
- Links never rot silently.

**Non-Goals:**
- New features to earn missing points (retrieval evaluation, feedback, logs-to-dataset are
  ROADMAP backlog items with their own changes).
- A documentation site generator (MkDocs etc.); Markdown on GitHub is what reviewers read.
- Rewriting folder `CLAUDE.md` files (they are for the coding agent, not reviewers).

## Decisions

1. **Two-layer README** (scan, then per-criterion) instead of a single long reference.
   Alternative: keep the current feature-oriented order; rejected because reviewers grade by
   criterion and miss evidence that sits under unrelated headings.
2. **Criterion sections follow the rubric order and use the rubric's names**, so a reviewer
   can tick them off; each ends with a "Check it" line (command or link).
3. **Detail in `docs/`, one file per concern**; the README keeps a 2-4 sentence summary per
   topic and links. The tool reference moves verbatim first (reviewable diff), then is tidied
   into one table plus per-tool notes.
4. **Numbers are copied from checked-in artefacts, never typed from memory**: the judge table
   above is regenerated by a small documented command (`uv run python -m evals judge` output
   or a one-off script in `scripts/`) and the source file is named next to each number.
5. **Self-evaluation table** with columns Criterion, Max, Claimed, Evidence (links). Bonus
   items not done (e.g. retrieval evaluation, logs to ground truth) appear with 0 and a link
   to ROADMAP backlog. The table is filled in last, after steps 1-9 land, from what is
   actually merged.
6. **Screenshots captured from the running compose stack** (browser automation or by hand),
   light theme, 1440×900, cropped to the relevant panel, PNG optimised under 500 KB; the demo
   is a GIF under 1000 KB or an external video link (YouTube/Loom) to stay under the
   pre-commit large-file limit. No screenshot shows a key, an email address other than a
   demo account, or a session token.
7. **Link check as a pytest test** (no network): Markdown links and images with relative
   targets must resolve to files; `#anchor` targets must match a heading slug (GitHub's
   slug rules); external `http(s)` links are not fetched. Alternative: a link-check GitHub
   Action (lychee); rejected for the default run because it needs network and is flaky, but
   it can be added to the evals-style manual workflow later.

## Risks / Trade-offs

- [Docs drift from the code after later changes] → link test catches moved files; each
  later change's tasks include a README/docs update (as the existing changes do).
- [Screenshots go stale after UI changes] → `docs/images/README.md` lists each image, the
  screen and the command to reproduce it.
- [Labels' provenance must be stated accurately] → `evaluation.md` must describe exactly how
  `labels.json` was produced (who or what voted, how disagreements were resolved) so the
  "manual evaluation" and "hand-crafted ground truth" bonuses are claimed only if true.
- [README too long again] → the scan layer is capped at about 80 lines; each criterion
  section at about 15 lines; anything longer moves to `docs/`.

## Migration Plan

Apply after steps 1-9 (the README is updated inside each of those changes too, so this
change mostly moves and condenses). Write `docs/` files first, then the README, then
screenshots, then the self-evaluation. Rollback: revert the commit; no code depends on the
docs except the link test, which is removed with them.
