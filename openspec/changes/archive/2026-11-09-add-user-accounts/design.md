## Context

See proposal.md for motivation and `openspec/ROADMAP.md` ("Identity and tenancy") for the
decisions shared with the other changes. State of the code this builds on:

- `api/main.py` installs `OriginGuard` (Host must equal the configured origin; unsafe methods
  need the same `Origin`/`Referer`) and the redacting log filter. There is no notion of a user.
- Thread ids are generated by the browser (`THREAD_ID_PATTERN = ^[A-Za-z0-9_-]{1,64}$`) and
  accepted as-is by `/api/v1/chat/stream`, `/threads/{id}`, `/threads/{id}/report` and
  `DELETE /threads/{id}`. After `migrate-to-postgresql` (step 2) the history lives in the
  Postgres checkpointer and the workspace/usage/confirmation side tables in the async
  `storage/` layer (SQLAlchemy async + psycopg 3); `ThreadStore` is an async Protocol with a
  Postgres and a fake implementation, idle threads are purged after
  `thread_retention_days`, and "one turn per thread" is enforced across processes by the
  database. After `add-resumable-agent-turns` (step 3) each turn has a row in `turns`
  (status, reason, user message).
- `api/services/monitoring/` reads Logfire with the operator's read token and returns every
  session in the window; `v1_monitoring.py` has no access control.
- `app/telemetry.py` opens one `session_span` per turn tagged with `session.id` (the thread
  id) from `[telemetry.attributes]`.
- Per-turn secrets are already isolated with `commons.scoped_secret.ScopedSecret`
  (`ContextVar`), so concurrent turns do not see each other's keys.

## Goals / Non-Goals

**Goals:**
- Email + password accounts with verification and recovery that resist enumeration,
  credential stuffing and token theft at screening-tool scale.
- Every user sees only their own threads, reports and usage, through the API and through any
  in-memory state, with one ownership check in one place per resource.
- Monitoring (everyone's questions) only for admins.
- No secret or token in code, git, logs, spans or responses.

**Non-Goals:**
- OAuth / social login, SSO, MFA (a follow-up; the session model allows adding TOTP).
- Organisations or shared threads between users.
- Storing the OpenAI key per user (step 5) and the daily quota (step 6).
- Moving turns to a worker (step 7): this change keeps turns in the API process.

## Decisions

1. **Server-side sessions, not JWT.** A 256-bit random token (`secrets.token_urlsafe(32)`)
   goes in cookie `[auth].cookie_name`; Postgres stores `sha256(token)` with `user_id`,
   `created_at`, `last_seen_at`, idle and absolute expiry from `[auth]`. Revocation (sign
   out, password change, reset, account deletion, sign out everywhere) is a row delete.
   *Alternative*: signed JWT in a cookie — rejected: cannot be revoked without a deny list,
   and the API already has a database. Cookie flags `HttpOnly; Secure; SameSite=Lax;
   Path=/`; `Secure` is relaxed only when `[auth].cookie_secure = false` for plain-HTTP local
   runs, and loading settings refuses `false` when `[telemetry].environment = "production"`.
2. **CSRF.** `SameSite=Lax` plus the existing `OriginGuard` (unsafe methods must carry the
   app's own `Origin`) cover cross-site posts; no separate CSRF token. The guard's allowed
   origin becomes configurable for the deployed host (step 1/9 already change the bind
   address); this change only depends on it being enforced.
3. **Argon2id via `argon2-cffi`** with parameters from `[auth.argon2]` (time cost, memory
   cost, parallelism; library defaults RFC 9106 low-memory profile). `check_needs_rehash`
   upgrades hashes on sign in. Password policy from `[auth]`: minimum length 12, maximum 128,
   rejected if it equals the email; no composition rules (NIST 800-63B). *Alternative*:
   bcrypt — rejected (72-byte truncation, weaker against GPUs).
4. **Single-use tokens for verification and recovery.** One table `auth_tokens(purpose,
   user_id, token_hash, expires_at, used_at)`. Raw token only in the emailed link (fragment
   `#token=` so it is not sent in `Referer` or server logs; the page posts it in the body).
   Consuming it is one `UPDATE ... WHERE used_at IS NULL AND expires_at > now() RETURNING`
   so two concurrent uses cannot both succeed. A new token for the same purpose invalidates
   earlier ones. Lifetimes from `[auth]` (verification 24 h, reset 30 min).
5. **No enumeration.** Sign-up, resend-verification and forgot-password always answer 202
   with the same body; when the email is taken or unknown the mail sent (or not) differs, the
   response does not. Sign-in failure is one message for an unknown email and a wrong
   password; only a correct password on an unverified account returns the distinct
   `verification_required` state (knowing the password proves ownership). Timing:
   an unknown email still runs one Argon2 verification against a fixed dummy hash, and mail
   is sent from a background task so its latency is not on the response path.
6. **Throttling in Postgres.** `login_attempts(key, window_start, count)` keyed by
   `email:<normalised>` and `ip:<address>`; limits and window from `[auth.throttle]`. Over the
   limit: 429 with `Retry-After`, the password is not checked. The client address comes from
   the socket, or from `X-Forwarded-For` only when `[auth].trusted_proxy_hops > 0` (Caddy in
   step 9). *Alternative*: Redis counters — rejected here because Redis arrives only in
   step 7; the store is behind one small interface so it can move later.
7. **Roles as a column** `users.role in ('user','admin')`. `require_admin` dependency on the
   monitoring router. Non-admins get **404**, not 403, so the endpoints do not advertise
   themselves. `create-admin --email` creates a verified admin or promotes an existing
   account, reading the password with `getpass` (never an argument or env var); it refuses if
   stdin is not a TTY unless `--password-stdin` is given (for scripted deploys).
8. **Ownership in the repository layer, not in handlers.** Every `storage/` repository method
   for a tenant resource (threads, `turns`, workspaces, pending confirmations, supplied and
   declined values, usage) takes `owner_id` as a required argument and puts it in the
   `WHERE`; both `ThreadStore` implementations (Postgres and fake) honour it, and the shared
   contract tests run the crosswise cases against both. `turns` gains `user_id`.
   A thread row is created on the first turn with the caller as owner; a later request with
   that id from another user finds no row → 404 (`UNKNOWN` message today). Client-chosen ids
   are kept (no contract change) but are namespaced: the uniqueness key is
   `(owner_id, thread_id)` and the LangGraph checkpointer's `thread_id` becomes
   `f"{owner_id}:{thread_id}"`, so two users picking the same id never share a checkpoint.
   *Alternative*: server-issued thread ids — cleaner, but changes the wire contract and the
   frontend store; namespacing gives the same isolation.
9. **In-memory isolation.** Whatever per-turn state stays in process memory (the live
   workspace being projected, the event sequence, the fake store's maps) is keyed by
   `ThreadKey(owner_id, thread_id)`, and the database's one-active-turn constraint becomes
   unique on `(owner_id, thread_id)`; the router builds the key from the session, never from
   the body. Per-turn secrets keep using
   `ScopedSecret`. No module-level mutable state may hold user data; a test scans `api/` for
   module-level dict/list/set assignments outside an allow-list.
10. **Telemetry tenant tag.** `session_span` gets a new attribute `[telemetry.attributes].user_id`
    holding the user's UUID (random, not derived from the email). The admin Monitoring
    listing adds `owner` resolved from Postgres; emails never go to Logfire. The Logfire
    read token stays server-side and only admins can trigger a query.
11. **Frontend.** A new `features/auth/` with the five screens rendered by `App.tsx` when
    `GET /api/v1/auth/me` answers 401, using existing tokens, `.glass` surface, inputs and
    buttons from `components/ui` per `frontend/DESIGN.md`, each with loading, error and
    success states. `apiClient` turns any 401 into "signed out" and shows sign-in, keeping
    nothing in browser storage. The rail adds an Account entry above Settings and hides
    Monitoring unless `me.role == "admin"`. Overview, Map and Chat components are unchanged.

## Risks / Trade-offs

Threat model (assets: other users' threads and reports, the operator's Monitoring data,
accounts):

- **Credential stuffing / brute force** → Argon2id cost, per-email and per-IP throttling,
  generic errors. Residual: distributed attacks across many IPs; acceptable at this scale.
- **Account enumeration** → identical responses for sign-up/forgot; dummy-hash timing;
  mail sent off the request path. A test compares status, body and a coarse timing bound.
- **Session theft** → `HttpOnly` (no JS access), `Secure`, hashed at rest (a DB leak gives
  no usable cookie), idle and absolute expiry, rotated on sign in (session fixation).
- **Recovery token theft** → hashed, single-use, 30 min, in the URL fragment, all sessions
  revoked on reset.
- **IDOR on thread ids** → owner in every query, namespaced checkpoint ids, 404 for foreign
  ids; a test signs in two users and calls every thread route crosswise.
- **Cross-tenant leakage through memory** → owner-keyed in-memory maps, `ContextVar`
  secrets, the module-state scan.
- **Monitoring leaks everyone's questions** → admin-only, 404 for others.
- **Email deliverability** blocks sign-up in production → the operator configures SMTP
  (e.g. Amazon SES) in step 9; `create-admin` works without mail.
- **Trade-off**: client-chosen thread ids remain guessable within one account; harmless
  because they are only valid for their owner.

## Migration Plan

1. Alembic migration adds `users`, `sessions`, `auth_tokens`, `login_attempts`, a non-null
   `owner_id` on thread tables and a non-null `user_id` on `turns`. Existing local threads (pre-accounts) have no
   owner: the migration deletes them (local scratch data; stated in the README).
2. Deploy order: migrate, run `create-admin`, then start the API. Without any user the UI
   shows sign-up.
3. Rollback: the down migration drops the new tables and column; the previous image runs
   without accounts.

## Resolved Questions

- SMTP configuration (decided 2026-11-09, during implementation): the SMTP server (host, port,
  STARTTLS, login, password, sender) is configured only in `.env`, one place for Docker and native
  runs; `[mail]` names the variables (as `[database]` does for `DATABASE_URL`) and keeps the link
  origin and time limit. A missing or invalid value stops start-up naming the variable. Inside a
  container a loopback host means the `mailpit` service, so one `.env` serves both run modes.

- Server-wide API keys (resolved during implementation, after the security audit): the key routes
  of `/api/v1/settings` save to the server's keychain, which every user's turns use. Saving and
  clearing a key is therefore admin-only (403 with a fixed message); the status routes stay
  available to every signed-in user. Per-user keys replace this in step 5 (BYOK).

- Sign-up is open for the capstone deployment (decided 2026-11-07), so peer reviewers can
  create an account without asking. `[auth].signup_open = true` is shipped and the operator can
  close it; email verification, login throttling and the daily quota (step 6) cap abuse, and
  BYOK means each user's model calls are billed to their own OpenAI key.
